Design document

Review Assist

Turn an AI coding agent's session into a guided, mechanically verified pull-request review, without the session transcript or the code ever being stored by the service.

Status shipped, v1.0.4 (MCP server) Format Intent Document, schema 0.1 (frozen) Licence Apache-2.0 Companion Low-level design

Section 1

Overview

Review Assist is three cooperating pieces and one file format. A developer's coding agent runs a local MCP server that distils the session into an Intent Document: what was asked, what was assumed, what was tried and abandoned, what was actually verified, and a guided tour of the diff with every stop anchored to real hunks. A deterministic validator refuses to write the document unless it demonstrably covers the change. The document is committed to the branch at .intent/<branch>.json and travels with the code. A GitHub App reacts to every push on the pull request, recomputes coverage, posts a check and a summary, and serves a browser view that walks a human reviewer through the change assumption by assumption and hunk by hunk.

The format

Six sections: meta, problem, assumptions, approach, tour, verification. JSON Schema 2020-12, version 0.1, deliberately frozen.

The producer

An MCP server over stdio that hosts a two-agent author/reviewer distillation. It never calls a model. It computes ground truth, serves source material, and gatekeeps the result.

The consumer

A stateless Cloudflare Worker: webhook automation as the app bot, plus an OAuth broker and thin GitHub proxy behind a client-side viewer.

The architectural centre of gravity is a single claim: the document must be earned, not asserted. An agent writing a summary of its own work is a press release. So the producing side is split into two role-locked contexts that cannot reach each other's tools, an interview between them is recorded and attested by the server rather than narrated by either side, and the finished document is admitted only after five deterministic checks it cannot argue with.

The one-line version

Agents write code faster than anyone can read diffs. The context that makes review fast is thrown away the moment the PR opens. Review Assist captures it at the source and proves, mechanically, that what it captured actually explains the change.

Section 2

Problem statement

2.1 What is breaking

Code review was designed around an assumption that no longer holds: that the person who wrote the change is available, remembers why, and produced it slowly enough that reading it back is proportionate work. With an agent in the loop, a 600-line change can arrive in twenty minutes, and the only durable artefact is the diff.

Everything that makes a review fast is discarded at exactly the moment it becomes useful:

  • The ask. What the human actually requested, in their own words, and how it drifted. Scope creep and half-finished migrations hide in that drift.
  • The assumptions. The things the change takes to be true about the world, which the diff cannot show and which are the cheapest thing to check and the most expensive thing to get wrong.
  • The road not taken. What was tried and abandoned, and why. A reviewer who does not know an approach was already rejected will propose it.
  • The verification boundary. What was actually exercised, and, more importantly, what was not. Authors go quiet about the second half.

2.2 Why the obvious fixes do not work

Obvious fixWhy it fails
Ask the agent to write a PR description It is diff-inferred, not session-derived. The agent restates what the code already says, smooths over what it guessed, and nothing checks whether the description covers the change. It is unfalsifiable by construction.
Dump the transcript into the PR Raw sessions are roughly 95% machinery. Measured across 41 sessions in one workspace: 85 MB of transcript, of which actual conversation is a median 4.8%. It also leaks secrets, internal chatter, and dead ends with equal billing.
An AI reviewer that reads the diff It has the same information the human has, which is the information that is missing. It can find bugs; it cannot tell you what the user asked for.
Make developers write it by hand The context is already gone by the time the PR opens, and the work is charged to the person least motivated to do it.

2.3 The problem, stated

Capture the intent behind an agent-authored change at the source, while the session is still live; make the capture verifiable rather than merely plausible; and deliver it to a human reviewer inside the pull request they were going to open anyway, without storing their code and without asking them to install anything.

Four constraints follow directly from that sentence, and they shape everything downstream:

  • At the source means the producer runs on the developer's machine, in the agent's own session, with access to the transcript.
  • Verifiable means a deterministic checker, not a model, decides whether the document is admissible.
  • Inside the pull request means GitHub holds every durable piece of review state, and the service adds no second place to look.
  • Without storing code means the service has no database, and the transcript never leaves the machine that produced it.

Section 3

Requirements

3.1 Functional requirements

IDRequirementDetail and rationale
FR-1Derive the document from the session, not from the diff Every claim traces to something that happened in the authoring session, or to the code itself. This is the property diff-only tools cannot replicate, so it is the first requirement rather than a nice-to-have.
FR-2Split production into two role-locked contexts An Author that holds the transcript and answers, and an Intent Reviewer that reads the diff cold, interrogates, and writes. Neither may hold the other's tools.
FR-3Make the interview two-sided and server-attested Questions are recorded and hashed to a q_id; answers are filed against that id by the author itself. meta.interview reports what the server witnessed, overriding anything the agent self-reports.
FR-4Let a repository teach the reviewer its own questions A committed .reviewer/ folder of markdown house rules is served to the reviewer after the diff and before round one. It may add questions; it may never relax a check or excuse the interview.
FR-5Gate the write behind deterministic validation Five checks: schema, staleness, coverage, cross-references, secret redaction. Coverage is the load-bearing one: the union of tour anchors must cover every substantive diff hunk.
FR-6Commit the document with the code .intent/<branch>.json, reviewed like any other file, versioned like any other file, and excluded from its own coverage denominator.
FR-7Require explicit per-repository consent The server is installed once, globally. It must not silently write into every repository the developer touches. Decisions are always, once or never, stored per user and outside any repo.
FR-8Report automatically on every push On opened, synchronize and reopened: a check run, a sticky summary comment carrying the coverage count and the guided link, and a managed block in the PR description.
FR-9Serve a guided review, assumptions first Front page of problem, assumptions and approach, then the anchored tour in narrative order, a coverage overlay that badges unexplained hunks, and a verification panel that leads with not_verified.
FR-10Write review output as the human, not as a bot Comments, replies and the verdict post with the signed-in reviewer's own token. Automation output posts as the app. The two identities never blur.
FR-11Degrade to markdown The PR description block renders the document for anyone who never opens the viewer, so the artefact has value with zero clicks.
FR-12Return findings to the live session The reviewer role's closing message (unanswered questions, everything in not_verified, defects exposed by reading the diff cold) reaches the session while the code can still be changed. The document is the after-the-fact half.

3.2 Technical requirements

IDRequirementDetail and rationale
TR-1MCP over stdio, Node 18+, one bundled file Distributed as review-assist-mcp on npm (runnable through npx) and as a one-click .mcpb bundle. esbuild inlines the role templates, so there is exactly one artefact to ship.
TR-2The server never calls a model Generation is delegated to the calling agent through a guide. The server computes ground truth, serves source, and validates. That keeps it deterministic, testable, free to run and free of an API key.
TR-3No response may grow with the size of the change Diff, spine, transcript windows, house rules and answers are all paged with a cursor, default 20 KB per page. Opening a run returns a hunk index and a handle, never diff text.
TR-4Role isolation must be structural REVIEW_ASSIST_ROLE decides which tools are registered at all, so the other role's tools are absent rather than disallowed. A client-side allowlist is belt and braces, not the mechanism.
TR-5Both roles must derive the same run handle without speaking run_id = sha256(repo | base_sha | branch). The head SHA is state on the run, not identity, so committing the document (itself a commit) does not orphan the interview.
TR-6Run state on disk, outside the repository ~/.review-assist/runs/, beside the consent file. The roles are separate processes, and a reviewer has resumed a run eleven hours later across a restart. Interview scratch state has no business in a pull request.
TR-7One diff, produced in one place compute_diff, read_diff and submit_document all go through the same function, with .intent/ excluded at source. Hunk ids handed out, text paged, and the diff validated against therefore cannot disagree.
TR-8The application holds no state No KV, D1, R2 or Durable Objects. The session is an encrypted HTTP-only cookie (AES-GCM); decrypting it is the entire session lookup.
TR-9Repo content must never enter a shared cache Documents, diffs and file context are served Cache-Control: private, no-store. A shared cache entry is content at rest and an access-control bypass. Static assets are edge-cached aggressively; they carry no repo content.
TR-10Two distinct GitHub identities A short-lived installation token (App JWT, RS256, exchanged per event) for automation output; the signed-in reviewer's user-to-server token for everything a human is accountable for.
TR-11Webhook must verify and return fast HMAC-SHA256 signature check with a constant-time compare, then a 202 inside the budget with the GitHub round-trips moved into waitUntil.
TR-12Treat repository content as untrusted data .reviewer/ and .intent/ are both editable from a fork's pull request. House rules are framed as reference material that cannot override the protocol; rendered markdown is sanitised and mermaid sandboxed before display.
TR-13Agent-portable Claude Code and Codex are first-class, with a generic fallback. Role prose lives once in agents/_roles/; each environment supplies only a thin container template, so the three copies cannot drift.
TR-14The schema is the contract JSON Schema draft 2020-12 is normative; TypeScript types mirror it. Version 0.1 is frozen because a change ripples through the validator, the viewer, and every document already committed.

3.3 Non-functional requirements

IDQualityTarget and how it is met
NFR-1Privacy The session transcript never leaves the developer's machine. The application has no database and stores no code at rest; it reads document and diff from GitHub per request with the reviewer's own token and holds them in memory for the length of that request. Code does pass through the hosted service in transit, which is stated plainly rather than glossed, and self-hosting is the answer for teams where that matters.
NFR-2Adoption friction A declared budget of exactly two one-time installs: the MCP server on the developer side, the GitHub App on the repository side. No workflow file, no CI minutes, no secrets, and no per-reviewer browser extension. Reviewers sign in once.
NFR-3Non-blocking by default The check run never concludes failure. Missing document or incomplete coverage is neutral; full coverage is success. A tool that blocks merges on day one gets uninstalled on day two.
NFR-4Distillation latency Measured, not estimated: median 1400 s from run open to submit over 15 runs, range 389 s to 2242 s. The largest single phase (670 s, 48%) was the two roles waiting on each other, which seeding the standing questions at run open collapses to the longer of the two independent reads.
NFR-5Cost Free, with no paid tier. The server calls no model and runs as a child process; the application is a single stateless Worker that fits a free tier.
NFR-6Honesty of the artefact Fields carry provenance markers (from_transcript, confirmed_in_interview, inferred_from_code). What the interview could not resolve is listed as an open question rather than smoothed over. The server attests interview counts so a document cannot claim a rigour it did not have.
NFR-7Reviewer time to first judgement The front page is designed so a reviewer can reject the framing in about two minutes without reading a line of code: problem, out of scope, assumptions with blast radius, open questions, approach with rejected trials.
NFR-8Openness and portability Apache-2.0, fully self-hostable (one stateless container plus the operator's own GitHub App registration). The hosted instance is a convenience, not a dependency. The format is published so other producers and renderers can exist.
NFR-9Operability No database means no migrations, no backups and no data-retention policy to write. CI builds, typechecks, tests, validates the example document, and fails if generated files are stale or release metadata is inconsistent.
NFR-10Failure behaviour Every gate returns a typed, actionable failure rather than a refusal: the consent prompt carries its options, head drift names both SHAs and the fix, unknown anchors list the valid ids, and validator failures return findings plus uncovered hunk ids. Nothing is written on any failing path, and the run with its attested interview survives.

3.4 Non-goals

  • Not a bug finder. The Intent Reviewer's job is to interrogate intent and anchor it to the diff. Defect hunting is a side effect of reading the diff cold, reported in its closing message, not the product.
  • Not a gate on merge. Merging stays on GitHub, and the check stays advisory.
  • Not a replacement for human review. The output is a better-prepared review, not a substitute verdict.
  • Not a diff renderer for the native GitHub page. A GitHub App cannot modify that view; overlaying it was considered and rejected (see 4.5).
  • Not multi-repo, yet. One document describes exactly one commit range in one repository. Cross-repo linking is designed but not built.

Section 4

Approach

The system is shaped by one asymmetry: the expensive, privileged, context-rich work happens on the developer's machine, and the cheap, public, stateless work happens in the cloud. Every boundary in the design follows that line. Anything that needs the transcript stays local. Anything that needs to be durable goes to GitHub. The service in the middle owns nothing.

4.1 High-level design

Three systems and two external actors. The developer's machine produces the change and its Intent Document. GitHub stores the pull request and every durable piece of review state. The Review Assist application reacts to events as a bot, then serves the guided review as a proxy for the signed-in human.

4.2 Data flow

The high-level view says which systems talk. This one says what actually moves, where it rests, and which line it must never cross. Four trust zones, read top to bottom: the developer's machine, GitHub, the Worker, and the reviewer's browser.

4.3 Sequence

End to end, in two parts, because the two halves share almost no participants. The first is the distillation on the developer's machine, where the interesting thing is that the two roles start together, read independent things, and meet only through the run file. The second is what happens once the pull request exists.

4.4 Key design decisions

4.4.1 Two roles, enforced by tool registration

A single agent summarising its own session produces a document with no adversary in it. The split gives the Author the transcript and the Reviewer the diff, and lets the Reviewer, which knows nothing about intent, decide what has to be asked. The enforcement matters as much as the split: REVIEW_ASSIST_ROLE determines which tools the server registers, so the other role's tools are not present to be misused. A client-side allowlist alone would be a suggestion.

The Reviewer has no filesystem tools at all, which is why the repository's own house rules arrive through get_reviewer_instructions rather than through a file read: handing it a general read tool to pick up .reviewer/ would open the door to the transcript, and the whole isolation is that everything it knows about intent it had to ask for.

4.4.2 The interview is attested, not narrated

If the Reviewer reported both halves of the conversation, the server could not distinguish a real interview from an invented one. So record_interview_round returns a q_id per question, the Author answers by id through its own tool, and each round records answered_by. A Reviewer transcribing on the Author's behalf is still allowed and still recorded, but marked reviewer-sourced rather than attested. At submit time the server stamps meta.interview from what it witnessed, overriding whatever the document claimed.

Rounds are keyed by a hash of the question text, so recording is an upsert: retrying cannot inflate the count, which is what makes the number worth attesting at all.

4.4.3 The run handle is content-addressed

run_id = sha256(repo | base_sha | branch). Two processes that are forbidden from talking derive the same handle from compute_diff alone, and a Reviewer resumed hours later recomputes it rather than remembering it. The head SHA was once part of that hash and was removed: committing the Intent Document is itself a commit, so the correction cycle the protocol promises used to destroy the attestation it was meant to preserve. The head is now state on the run, moved forward on open, with the previous value kept in head_history.

4.4.4 Coverage is the load-bearing check

Schema, cross-references and redaction catch malformed documents. Coverage catches dishonest ones. Every tour stop carries anchors pinned to the head SHA; the union of those anchors is compared against the actual diff hunks, and any substantive hunk nobody explained is reported as an unexplained change. This is the check that makes the document falsifiable, and therefore the check that makes the rest of it worth reading.

.intent/ is excluded from the denominator (a document must not have to explain its own file) and is excluded from the diff at source rather than filtered downstream, because it sorts first in git's path order and would otherwise shift every hunk id by one whenever the document was committed.

4.4.5 GitHub is the database

Every durable piece of review state (the document, the diff, the check, the comments, the verdict) already has a home in the pull request. Adding a second home would mean a database, a retention policy, an access-control model that has to agree with GitHub's, and a copy of the customer's code at rest. The application therefore holds nothing: the reviewer's session is an encrypted HTTP-only cookie, repo content is fetched per request with that reviewer's own token, and every response carrying it is private, no-store.

4.4.6 Two identities, never blurred

Automation output posts under a short-lived installation token as the Review Assist bot. Comments, replies and the verdict post under the signed-in reviewer's token as that human. A verdict attributed to a bot is worthless; automation attributed to a human is misleading.

4.4.7 Consent before the first write

The MCP server is installed once and then present in every repository the developer opens. submit_document therefore refuses on an unknown repository and returns a prompt with three options rather than an error. always and never persist to ~/.review-assist/consent.json; once lives in memory for the life of the process and is never written down.

4.5 Rejected alternatives

OptionVerdictReasoning
Browser extension overlaying the native GitHub diffRejected In-place rendering is a real advantage and it still lost: a per-reviewer install is outside the friction budget, and the implementation would be hostage to GitHub's DOM.
Pure static viewer on GitHub PagesRejected, design retained Zero infrastructure and the strongest privacy story, but private-repo auth is blocked because GitHub's OAuth token endpoint sends no CORS headers. The alternatives were pasting a personal access token or running a proxy. The stateless-renderer design survives inside the App.
A CI action instead of a GitHub AppRejected as the default Requires a workflow file, secrets and runner minutes in every repository. The CLI remains available for teams that prefer to run the same checks on their own runners.
Server-side generation (the MCP server calls a model)Rejected It would need an API key, add cost, make the server non-deterministic, and mean shipping the transcript somewhere. Generation is delegated to the agent already in the room.
One agent writing its own documentRejected No adversary, no interview to attest, and every claim self-certified. The two-role split exists precisely to make the document cost something to produce.
Keeping interview state in memory, keyed by repo pathRejected after failure In a workspace holding several repositories the server's working directory and the submitted repo path resolve differently, so rounds were filed under one key and looked up under another. Observed: 21 record calls for 7 questions and four submits of the same document. State moved to a content-addressed file on disk.

Section 5

State of play

5.1 What is built

packages/schema

JSON Schema 2020-12 plus mirrored TypeScript types. Frozen at 0.1.

packages/validator

The five checks, the diff parser and hunk indexer, the pager, the markdown renderer, and a CLI.

packages/mcp-server

Sixteen tools, the role split, the run store, the spine builder, per-agent transcript parsers, consent.

apps/github-app/worker

Webhook automation, OAuth broker, GitHub proxy. Stateless Cloudflare Worker.

apps/github-app/viewer

Client-side guided-review SPA, plus the public landing page at reviewassist.dev.

5.2 Measured behaviour worth knowing

1400 s

Median distillation, run open to submit, over 15 real runs. Range 389 s to 2242 s.

4.8%

Median share of a raw transcript that is actual conversation. The spine keeps that and marks the rest.

40 of 41

Sessions whose entire conversation spine fits in a single tool call, median ~11,900 tokens.

2

Interview batches, capped. Three observed runs opened a third round after the Author had handed back, which nothing could answer.

5.3 Open questions

  • Anchor durability across force-pushes. Re-anchor by content hash of the hunk rather than by line range? Today a moved head renumbers hunks and costs a re-anchor.
  • Quoting policy in public repositories. How much of problem.user_asks is safe to quote verbatim by default, and should the redaction level be a per-repo setting?
  • Interview budget. Fixed at two batches, or budget-based on the size of the change?
  • Cross-repo features. An additive feature block with a globally unique id stamped into every sibling document, with PR links resolved live at view time. Designed, agreed, not built.
  • Richer authored content. Optional markdown body per section and mermaid diagrams, which would require a schema bump and the sanitising and sandboxing rules that go with rendering untrusted repository content.
