Section 2

Schema package

src/intent-doc.schema.json is normative (JSON Schema draft 2020-12). src/index.ts exports the raw schema object for Ajv plus TypeScript interfaces that mirror it, so the validator, the MCP server and the viewer all speak the same shape without a code generator in the build.

schema_version is "0.1" and frozen. Any change ripples through the validator, the Worker's mirror, the viewer, and every document already committed to a branch, so a format change is an issue before it is a pull request.

Section 3

Validator package

3.1 Diff parsing and the hunk index

src/diff.ts parses unified diff text into DiffFile[], each with DiffHunk entries carrying old_start, old_lines, new_start, new_lines and a substantive flag. A hunk is substantive when at least one added or removed line has non-whitespace content; pure whitespace churn is parsed, counted and then ignored by the default coverage threshold.

indexHunks() assigns stable, human-usable ids (H1, H2, …) in git's own path order. Those ids are the entire vocabulary the Reviewer role uses to talk about the change: they appear in compute_diff's index, in read_diff requests, and in the anchor expansion at submit time. Because one function produces the diff for all three, an id always means what it meant when it was written down.

Range overlap

Coverage and anchor matching both reduce to interval overlap on the new side of the diff. newRange(hunk) yields [new_start, new_start + max(1, new_lines) - 1], and rangesOverlap(a, b) is the standard a0 ≤ b1 && b0 ≤ a1. Using an inclusive range with a floor of one line is what makes a pure deletion hunk (new_lines: 0) anchorable at all.

3.2 Paging

src/page.ts bounds every response that could otherwise scale with the size of a change. DEFAULT_PAGE_BYTES is 20,000. pageDiff() cuts on hunk boundaries and returns a cursor; a caller follows next_cursor until it is absent. summarizeFiles() produces a per-file overview so a reader can decide what to page in rather than paging everything.

Why the server pages rather than the client truncating

MCP does not tell a server what its client's tool-result cap is, so the ceiling here is a guess. It is still worth more than the client's certainty: the server can stop on a hunk boundary and hand back a cursor, where a client can only truncate or spill the whole result to a file. That difference cost a real run: a 234,337-character compute_diff response was spilled whole to disk, and the run_id inside it became unreachable to a Reviewer that has no file access.

3.3 The five checks

validate(doc, opts) returns {ok, findings[], coverage?}. Findings carry a check, a severity of error or warning, a message and optionally a path. ok is false when any finding is an error.

#CheckImplementation
1Schema Ajv 2020 with allErrors. If the document does not parse structurally the function returns immediately: every other check would be reporting on rubble.
2Staleness meta.commit_range.head_sha against the actual head, compared by prefix so a short SHA and a full one agree. Failure message names both and says to regenerate.
3Coverage Flatten every tour[].anchors into {path, range, ref}, walk every diff hunk, and mark both directions. A substantive hunk no anchor overlaps becomes an unexplained error; an anchor no hunk overlaps becomes a dangling warning. Verification anchors do not count: only tour stops explain. strictCoverage promotes whitespace-only hunks into the denominator.
4Cross-references assumptions[].depends entries beginning T, tour[].parent and the id references in tour[].why must resolve to real ids.
5Redaction Every string in the document is walked against six patterns: AWS access key id, GitHub token, Slack token, private key block, generic api_key/secret/ password/token assignment, and a connection string carrying credentials. Callers may add more through extraSecretPatterns. A hit is a hard error.

The .intent/ exclusion, and why it is subtle

The document travels in the same pull request it describes, so it must not have to explain its own file. Coverage excludes .intent/ paths from the denominator but deliberately not from anchor matching. An earlier version skipped those files outright, which meant an anchor pointing into one could never be marked as matched, so the dangling pass reported a hunk id taken straight from compute_diff's own index as a possible stale anchor. The authoritative fix lives upstream in the MCP server, which excludes .intent/ from the diff at source; this path now exists for hand-written documents and diffs produced elsewhere.

3.4 Renderers and CLI

renderMarkdown() produces the full document view; renderPrDescription() produces the compact block the Worker manages inside the PR body. orderTour() walks the parent tree into display order. The review-assist CLI exposes validate and render, so teams that prefer their own CI can run exactly the checks the App runs.

Section 4

MCP server

4.1 Process model and the role gate

One stdio process per agent session, spawned by the client, bundled by esbuild into a single ESM file with the role markdown and TOML templates inlined as text. It calls no model and makes no network requests. The repository it operates on is REVIEW_ASSIST_REPO or the process working directory.

The role gate is four lines and is the whole enforcement mechanism: 

const ACTIVE_ROLE = activeRole();                       // from REVIEW_ASSIST_ROLE
const registerTool = (name, ...rest) => {
  if (ACTIVE_ROLE && !ROLE_TOOLS[ACTIVE_ROLE].includes(name)) return;
  return server.tool(name, ...rest);
};

An Author instance therefore has no submit_document to call and a Reviewer instance has no read_transcript, whatever the agent driving it decides to try. Claude Code's subagent tools: allowlist and Codex's per-agent MCP configuration both point at the same constant, generated from ROLE_TOOLS rather than hand-maintained, because the two copies drifted the moment a tool was added.

Role definitions on disk

Role prose lives once in agents/_roles/{author,reviewer,questions}.md. Each environment supplies a thin container template that wraps it: YAML frontmatter for Claude Code, TOML for Codex, bare markdown otherwise. get_role_definitions({install: true}) renders and writes them to ~/.claude/agents/intent-{author,reviewer}.md or ~/.codex/agents/intent-{author,reviewer}.toml. The environment is resolved from the MCP initialize handshake's clientInfo.name, with an explicit override and a generic fallback rather than a guess.

Installation is user-scoped, never project-scoped, and is preceded by a sweep. Two kinds of residue are removed, for different reasons. Project-scoped copies are always wrong: an earlier version told agents to place the files themselves, which landed them in whatever directory the agent happened to be in, and Claude Code prefers a project-scoped subagent over a user-scoped one, so a forgotten copy silently shadows the real definition. User-scoped copies are legitimate, so only roles the current bundle no longer contains are removed. The sweep never touches a file that lacks the generated-file marker or one of two legacy signatures, and installRoles writes only when content actually changed, because Claude Code asks the user to restart whenever a definition file moves.

4.3 The run store

A run is the unit the interview belongs to. Records live at ~/.review-assist/runs/<run_id>.json (overridable with REVIEW_ASSIST_HOME), beside the consent file and deliberately outside any repository: .intent/ is committed with the code, and interview scratch state has no business in a pull request. On disk rather than in memory because the failure it must survive is real: the roles are separate processes, a machine can run nine of these at once, and a Reviewer has resumed a run eleven hours later across a restart. 

interface RunRecord {
  version: 1;
  run_id: string;            // sha256(repo | base_sha | branch)
  repo: string;              // absolute, resolved
  base_sha: string;          // identity
  head_sha: string;          // STATE: moves as the branch does
  head_history?: string[];   // every previous head, oldest first
  branch?: string;
  created_at: string;
  submitted_at?: string;     // absent until a document is written
  document_path?: string;
  updated_at?: string;       // what the sweep measures
  rounds: Record<string, InterviewRound>;   // keyed by question hash
  batches?: number;          // batches of NEW questions spent, cap 2
}

interface InterviewRound {
  q_id: string;              // hash of the normalised question text
  question: string;
  answer: string;            // empty until someone answers
  resolved: boolean;
  answered_by?: "author" | "reviewer";   // only "author" is attestation
  seeded?: boolean;          // standing question, not an interview round
  at: string;
}

Sweeping

openRun sweeps before it opens. Age is measured from updated_at, not created_at, because a single run now follows a branch from its first compute_diff to its merge, and a branch worked on for a month is a live run rather than an abandoned one. Open runs expire after 30 days of silence; submitted runs after 7, which is long enough to fix a finding spotted after the fact and short enough that finished work does not accumulate.

4.4 The interview protocol

Question identity

q_id is a hash of the normalised question text. Three properties fall out of that single choice:

  • Recording is an upsert. Re-recording a question the run already holds replaces it and does not spend a batch, so retrying an interview cannot inflate the count. That is what makes meta.interview worth attesting: it reports distinct questions asked, not tool calls made.
  • Both roles derive the same id without speaking. The standing questions are canonical constants, so the Author can answer them before the Reviewer has recorded anything.
  • Answers cannot be misfiled. An answer arrives with the id of the question it answers, not a position in a list.

The standing set

openRun seeds six questions that do not depend on the diff: the plan question (what was agreed, what was learned, how it ended), plus the five that guard fields a diff cannot fill, covering the verbatim ask, what was tried and abandoned, the assumptions about the world, what is genuinely incidental, and what was actually run versus never exercised. Seeding is additive and idempotent: a question already present keeps its answer, so backfilling an in-flight run cannot erase an attestation.

What is deliberately not seeded is anything needing the hunk index. The incidental question is asked by file, because otherwise the Author would have to page the diff to answer it, which is the Reviewer's pass and puts the serialisation straight back. Assigning hunk ids to plan items stays the Reviewer's own read of the change. An unanswered seeded question is not counted as an interview round, so rounds: 0 still means no Author ever ran.

The wording of the standing questions is canonical in runs.ts, not in the role markdown, because the id is a hash of the text: prose that drifts by a word produces a question the Author cannot answer by id. The role file describes what each one guards.

Batches and stalls

ConstantValueBehaviour
MAX_BATCHES2 Batches of new questions. Re-recording an existing question is a free retry. Three observed runs opened a third round after the Author had already handed back, which nothing can answer, and each burned an hour of the Reviewer polling for a reply that had nowhere to come from.
STALL_POLLS8 get_answers tracks polls per run. Eight polls with unanswered questions and no new answers is reported as a stall rather than left to spin.

Attestation

summarizeRun() produces the counts; attestedInterview() narrows them to the fields the schema declares. At submit time the server overwrites meta.interview with that value, so a document cannot claim a rigour it did not have. A Reviewer transcribing an answer on the Author's behalf is still allowed and still recorded, but lands as answered_by: "reviewer", which is one role's account of a conversation the server never witnessed.

4.5 Transcript discovery and the spine

Locating a transcript and reading one vary along different axes, so transcript/sources.ts locates and one parser per agent reads, and they compose rather than nest. A cloud session is stored by one system but written in another's format, which is exactly the case that breaks a single inlined function.

SourceWhere it looks
claude-codeThe Claude config directory (CLAUDE_CONFIG_DIR aware), project-keyed, walking ancestor directories so a session started in a subdirectory is still found.
codexCODEX_HOME or the default Codex session store.
cowork-localCowork's local store, which holds Claude Code-format sessions.
exportedSessions filed by import_session for runs whose transcript never existed on this machine.

Candidates are ranked by references to the changed file basenames and the branch name, with recency as the tiebreak, and each carries a bounded preview of its first user turn so the Author can recognise this session rather than the most recent one.

The spine

A raw transcript is roughly 95% machinery. Rather than searching it, spine.ts reads all of it and keeps the parts a human wrote or an agent said, marking rather than deleting the rest:

  • Both sides of the conversation. Roughly two thirds of the prose is the agent's, and it has to be: half a negotiation is the agent's side, and "yes, do that" means nothing without the proposal it answers. Of 23 trials found across seven real documents, only 6 were user redirects.
  • Structured questions with the answer chosen, because scope decisions often arrive as tool calls rather than prose.
  • Commands and edits as one-liners: what ran and what was touched, without the output that makes a transcript enormous.
  • Plan revisions as deltas, where the session kept a todo list. One session revised its list 31 times across 84 items, and a dropped item is an approach being abandoned.
  • Gaps, sparingly. Items carry their own transcript indices, so a turn at 2 followed by one at 9 already says 3 to 8 were elided. Only a gap holding a failure, or long enough to be a phase of work, is named.

Nothing is dropped to make it fit. An earlier version deleted assistant turns once the spine passed 600 KB, which is the worst possible thing to lose. The response is bounded by paging instead, cut on item boundaries, so a large session costs more calls rather than less material. The spine of 40 of 41 measured sessions fits in a single call, median around 11,900 tokens, and being complete it removes the failure mode retrieval can never rule out: an answer the Author simply did not find.

4.6 Diff production

git.ts shells out to git, read-only, with a 64 MB buffer. computeDiff() resolves both refs, then runs a three-dot diff (base...head) so the result is the branch's own changes since the merge base rather than everything that happened on the base meanwhile.

.intent/ is excluded here, at the single place a diff is produced, and this is load-bearing. From a branch's second commit onward the document arrives as a whole-file addition (630 lines on the run that prompted the fix). It sorts first in git's path order, so it landed as H1 and shifted every other hunk id by one whenever the document was committed, silently misanchoring any regeneration. Excluding it at source means compute_diff, read_diff and submit_document all see the same diff, so the ids handed out, the text paged and the diff validated against cannot disagree, and counting hunks in the raw diff still reproduces the index.

4.7 Repository house rules

<repo>/.reviewer/ holds markdown the repository wants asked about every change: an invariant a past incident bought, a migration that must be paired with a backfill, a directory whose churn is never incidental. It is served by get_reviewer_instructions, to the Reviewer alone, after the diff and before round one.

PropertyValue and reason
Readable extensions.md, .markdown, .txt. Anything else is listed but not read.
Limits50 files, depth 3, 64 KB per file, plus the caller's byte budget. House rules are hand-written, so these bound a mistake rather than a workload.
Served through a toolThe Reviewer has no filesystem tools by design. Granting it a read tool to pick up house rules would open the door to the transcript, so the folder arrives bounded, like the diff.
Trust levelUntrusted repository content: a fork's pull request can edit it. Both the tool description and the role prompt frame it as reference material that adds questions and cannot override the protocol, the schema or the sourcing rules.
CoverageUnlike .intent/, .reviewer/ stays inside the coverage denominator. A change to the house rules is an ordinary change the document should explain.

4.8 Consent

~/.review-assist/consent.json, keyed by resolved absolute repository path, honouring REVIEW_ASSIST_HOME. enabled and disabled persist; once is a Set in memory for the life of the process and is never written down. A corrupt or unreadable file is treated as empty rather than crashing the flow, which fails toward asking again rather than toward writing without permission.

4.9 The submit gate

submit_document is the only tool that writes into the repository, and it is the Reviewer's alone. Five conditions apply in order. Each returns a typed, actionable payload rather than a bare error, and no failing path writes anything.

Between gate 4 and gate 5

Anchors in the submitted document may be written as hunk ids, which expandAnchors() resolves against a diff recomputed from the run's own SHAs by the same function that handed the ids out. Unknown ids fail with the full list of valid ones and a hint to re-read them rather than guess. Only then does validate() run, against that same diff and the run's head SHA. On success the server also returns the rendered PR description, the coverage report, the attested interview, and any warnings, and marks the run submitted while leaving it open.

Section 5

Worker

5.1 Routing

One fetch handler. A host-only redirect runs before anything else: the session cookie carries no Domain, so a co-equal www origin would hand signed-in users a second session and loop them through OAuth. Everything that is not an API path falls through to the static SPA, which is edge-cacheable because it carries no repository content.

5.2 The webhook pipeline

  1. Verify. HMAC-SHA256 over the raw body against x-hub-signature-256, compared in constant time. An unsigned or mismatched request is a 401 before anything is parsed.
  2. Filter. ping answers pong. Only pull_request events with action opened, synchronize or reopened proceed; everything else is acknowledged and ignored.
  3. Defer. Return 202 immediately and move the GitHub round-trips into ctx.waitUntil, so the handler never risks the webhook timeout.
  4. Mint. Sign an App JWT and exchange it for a short-lived installation token.
  5. Read. Fetch .intent/<branch>.json at the PR head SHA as raw content, with the branch name slash-flattened, and the base...head comparison as a diff.
  6. Recompute coverage. A compact mirror of the validator's coverage pass: substantive hunks only, .intent/ excluded, anchors from tour stops, interval overlap. The webhook computes coverage only; schema, staleness, cross-reference and redaction are local submit_document concerns.
  7. Write three things, all as the bot: a sticky summary comment (upserted by searching for an HTML-comment marker in the existing comments), a check run, and a managed block in the PR description delimited by start and end markers so the author's own prose is never touched.

The check run never concludes failure. A missing document or incomplete coverage is neutral; full coverage is success. The title carries the count, for example 4/5 changes explained, and details_url deep-links into the guided review.

5.3 Sessions

The reviewer's GitHub token lives only inside an encrypted, HTTP-only cookie. The key is AES-GCM derived from a SHA-256 digest of SESSION_SECRET; the cookie value is base64url(iv).base64url(ciphertext). Decrypting it is the entire session lookup, which is what lets the whole application run with zero state. A stored exp is checked on open, and any failure to decrypt returns null rather than throwing, so a rotated secret logs people out instead of breaking the service.

The OAuth state is a second short-lived cookie carrying the return path and a random nonce, echoed back and validated in the callback as the CSRF guard.

5.4 Installation tokens

To act as the bot the Worker signs an App JWT with RS256 (iat backdated 60 seconds for clock skew, exp at 9 minutes, under GitHub's 10-minute maximum) and exchanges it at POST /app/installations/{id}/access_tokens. WebCrypto's importKey accepts only PKCS#8 for RSA while GitHub issues PKCS#1 keys, so a BEGIN RSA PRIVATE KEY block is wrapped into PKCS#8 before import and a BEGIN PRIVATE KEY block is used as-is.

Section 6

Viewer

A single-page app with a hash route of the form #<owner>/<repo>/pull/<number>, which is why the deep link in the check and the comment works without any server-side routing. Boot reads /api/me, then /api/document, then renders.

SurfaceContents
Overviewproblem and out_of_scope, then assumptions with per-assumption acknowledge and flag controls, open questions, and the approach summary with its trials. Flagging an assumption posts a PR-level comment as the reviewer. The goal is that the framing can be rejected in about two minutes without reading code.
TourStops in narrative order (orderTour walks the parent tree), each rendering its own anchored hunks with keyboard next and previous. attention notes surface inline. incidental stops collapse by default.
CoverageUnexplained hunks are badged, never hidden. The viewer computes this with its own copy of the parse-and-overlap pass so the badge does not depend on a server round-trip.
VerificationWhat was performed, what tests were added, and not_verified given prominence rather than a footnote.
CommentingLine-range selection inside a rendered hunk, threads with replies, and the verdict composer. Every write goes through the Worker with the reviewer's own token.

The same document also serves the public landing page, its FAQ structured data, and the release and blog routes, which is why the file is one large hand-written SPA rather than a framework build: the demo on the landing page calls the same render function the real viewer does, so a screenshot cannot go stale.

7.2 Build

  • MCP server: sync-version then esbuild to a single ESM file targeting Node 18, with --loader:.md=text --loader:.toml=text so the role templates are authored as real files and inlined at build time. The version is read from package.json at runtime rather than written as a literal, because a hand-maintained copy drifts the moment npm version runs.
  • Desktop bundle: mcpb pack produces review-assist-mcp.mcpb for one-click install in the Claude desktop app.
  • Worker and viewer: the viewer's stylesheet is built, the Worker is typechecked, and wrangler deploy ships both. Production deploys purge the zone cache, since static assets are edge-cached aggressively.

7.3 CI and release

  • CI on every push to main: build all packages, typecheck, run vitest, validate the example document with the built CLI, fail if generated files are not current (git diff --exit-code), and fail if release metadata is inconsistent.
  • Release consistency pins packages/mcp-server/package.json, manifest.json and server.json to the same version, and is checked both before and after the bump so a half-applied release cannot be published.
  • Publish is manual with a version input, a dry-run mode and a release-only mode: build, test, bump, commit and tag, publish to npm, pack the desktop bundle, cut the GitHub release, then register with the MCP registry after npm has the version.
